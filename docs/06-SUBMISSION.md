# 06 — Submission checklist and known traps

Run this before you consider the work done. Ordered by risk.

---

## TRAP 1 — `/out/` is gitignored. Your compliance report will not be committed.

**Confirmed:** `.gitignore:18` contains `/out/` (Next.js static-export default).
`git check-ignore` proves `out/compliance-report-BR.json` is excluded.

The brief lists as a required deliverable:

> A brief compliance report generated by your service (can be JSON, CSV, or
> text format) showing aggregated tax data for at least one country

If the demo writes to `out/`, that deliverable never reaches GitHub and the
reviewer never sees it. Note that git cannot re-include a file inside an
excluded directory, so `!out/compliance-report-*.json` does **not** fix it.

**Fix:** write generated reports to **`reports/`**, not `out/`.

```ts
// scripts/demo.ts
mkdirSync("reports", { recursive: true });
writeFileSync(`reports/compliance-report-${country}.json`, JSON.stringify(report, null, 2));
```

Then commit `reports/compliance-report-BR.json` and link it from `README.md`.
Verify with `git check-ignore -v reports/compliance-report-BR.json` returning
nothing.

## TRAP 2 — `data/yuno-tax.db` must remain generated

**Resolved:** `data/*.db` is gitignored and the database is not committed.
`npm run demo` seeds first, while `predev`, `prebuild` and `pretest` keep every
review path synchronized with `data/tax-rules.json` and
`data/transactions.json`. Recheck with `git ls-files data/yuno-tax.db`
returning nothing before submission.

---

## TRAP 3 — Vercel audit writes are per-instance

**Mitigated, with a documented limit:** the build seeds a populated SQLite
database, and each Vercel instance copies it to writable `/tmp`. Audit writes,
reads and reports work for the lifetime of that instance; seeded audit ids work
on every instance. A newly written id can still 404 if its read lands on a
different cold instance because `/tmp` is not shared. The live smoke test
verifies the write/read path, while the production migration remains a shared
Turso/libSQL or Postgres repository behind `lib/db.ts`.

## Requirement coverage the build plan did not state explicitly

Add these to whatever you are working on now. Each is named in the brief and
each is cheap.

**Idempotency (Requirement 1, explicit).**
> "Be idempotent: calling the same calculation twice with the same inputs
> should return the same result."

Store a `calculationFingerprint` (sha256 of canonical inputs + ruleset version)
on every audit row and state the guarantee in the README: the calculation is a
pure function of `(canonical inputs, transaction date, ruleset version)`. Every
request still writes its own audit row, because a compliance log that drops
events is broken. Optionally honour an `Idempotency-Key` header that returns
the stored record. Reference: `docs/reference/src/db/auditRepo.ts` →
`fingerprint()`, and `docs/reference/src/service/taxService.ts`.

**Timestamp variety in fixtures (Test Data, explicit).**
> "Timestamp variety to demonstrate date-based rule selection"

`data/transactions.json` must span the Brazil 2026-01-01 boundary and include
at least one pre-2024-12-01 Peru digital-services transaction. Reference:
`docs/reference/src/seed/transactions.ts` — `txn_br_0001` / `txn_br_0002` and
`txn_pe_0005`.

**Amount bands (Test Data, explicit).**
Small (under $10), medium ($10–$100), large (over $100) must all be present per
country. The reference fixtures already do this.

**Error/edge cases surfaced in the report (Requirement 2, explicit).**
> "Any error/edge cases encountered"

The compliance report needs an `edgeCases` block counting refunds, zero
amounts, exemptions, below-threshold hits and errors. Reference:
`buildComplianceReport` in `docs/reference/src/db/auditRepo.ts`.

## Final verification: the clean-clone test

Do this last. It is the only thing that proves the reviewer can run your work.

```bash
cd /tmp && rm -rf verify && git clone <your-repo-url> verify && cd verify
npm install
npm run db:seed
npm test
npm run demo
npm run dev &
sleep 5
curl -s -X POST localhost:3000/api/tax/calculate -H 'Content-Type: application/json' \
  -d '{"amount":199.99,"country_code":"BR","product_category":"digital_services"}'
curl -s "localhost:3000/api/tax/report?country=BR&from=2024-01-01&to=2027-01-01"
```

If any step needs a file that is not in the clone, an env var you did not
document, or a manual step not in the README, fix it before submitting.

Check these by hand:
- [ ] `reports/compliance-report-BR.json` exists in the clone
- [ ] `data/tax-rules.json` and `data/transactions.json` exist in the clone
- [ ] `ARCHITECTURE.md` is 200–400 words (`wc -w ARCHITECTURE.md`)
- [ ] README's first code block gets a stranger to a running server
- [ ] `docs/` is committed (it shows judgment; leave it in)

## What to say in the submission

Three sentences, no more. Lead with the design decision that is hardest to get
right, because that is what separates submissions:

> Tax rules are stored append-only and bitemporally: `validFrom/validTo`
> selects the rate that was law on the transaction date, while
> `recordedAt/supersededAt` selects what the system believed at calculation
> time, so editing a rate never alters a historical calculation. All money is
> integer minor units and all rates integer basis points, with per-currency
> exponents (CLP has none), so no tax amount is ever produced by floating-point
> arithmetic. Run `npm run demo` for a 20-second walkthrough of all three core
> requirements, including a live rate change proving historical immutability.
